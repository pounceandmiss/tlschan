Description

These packages add TLS to Tcl channels by stacking a TLS layer on a socket or any other bidirectional channel. Four backend packages share one channel layer and one command set and differ only in the TLS library underneath:

tlschan::wolfssl

wolfSSL.

tlschan::rustls

rustls with the ring crypto provider.

tlschan::mbedtls

Mbed TLS 3.6.

tlschan::openssl

OpenSSL 3.

Normally a program loads tlschan, which loads one backend and makes its commands ::tlschan::name. This page writes the commands that way. Each backend package also defines them in the namespace of its own name, such as ::tlschan::wolfssl, with the same syntax; requiring a backend directly pins it. Several backends can be loaded into one interpreter, together with tcltls (package tls).

tlschan takes the backends in the order given by the variable ::tlschan::prefer, set before loading it, else by the environment variable TLSCHAN_BACKEND, else openssl rustls mbedtls wolfssl. The first of them already loaded is chosen, else the first that loads. If none does, package require tlschan raises no TLS backend available (tried openssl, rustls, mbedtls, wolfssl) with errorCode TLS BACKEND.

namespace eval tlschan {variable prefer {mbedtls openssl}}
package require tlschan

Unless the command ::tls::socket exists already, tlschan also creates aliases ::tls::name for the chosen backend's commands, so that code written for tcltls runs unchanged. A tcltls loaded afterwards replaces them. A backend package by itself never touches ::tls. See COMPATIBILITY for differences from tcltls and tclmtls.

Only TLS 1.2 and TLS 1.3 are implemented. By default a client opened with tlschan::socket verifies the server's certificate chain against the system trust store and checks that the certificate matches the host name it connected to.

COMMANDS

tlschan::socket ?option value ...? host port

Opens a TCP connection with ::socket and stacks TLS on it with tlschan::import. Returns the channel name. -async (which takes no value), -myaddr and -myport go to ::socket. -autoservername bool, default 1, sets -servername to host when it is not given. All other options, after the defaults set with tlschan::init, go to tlschan::import; see OPTIONS.

Errors from ::socket (for example couldn't open socket: connection refused) and from tlschan::import are raised unchanged; when the import fails the socket is closed. The handshake is not part of this command: it runs on first use of the channel, see CHANNEL BEHAVIOUR. With -async, a failed connect is reported there, as in handshake failed: connection refused.

tlschan::socket -server command ?option value ...? port

Opens a listening socket with ::socket -server and returns it. -myaddr, -reuseaddr and -reuseport are passed to ::socket; -backlog is not supported. Every accepted connection is imported with -server 1, -model set to the listening socket, and the other options, then command is called with the channel, the client address and the client port appended, as for ::socket -server.

So all accepted connections share one configuration, and with it one session ticket key (see SESSION RESUMPTION): the first connection reads the files and evaluates the -password script, and later ones reuse the result. An import error (an unreadable -certfile, for example) closes that connection, is reported through bgerror, and command is not called; the next connection tries again. A -model given here replaces the listening socket.

tlschan::import channel ?option value ...?
tlschan::starttls channel ?option value ...?

Stacks a TLS layer on channel and returns the channel name, which is unchanged. channel can be any channel open for reading and writing. No data is exchanged until the handshake starts, see CHANNEL BEHAVIOUR. The options are described in OPTIONS. starttls is another name for import.

Options are checked and files loaded here: a bad option, file or password raises an error from this command and leaves the channel as it was.

tlschan::unimport channel
tlschan::unstack channel

Sends a close_notify alert if the handshake has completed, writes out pending TLS data and removes the TLS layer. The channel stays open and carries plain data from then on. Raises bad channel "chan": not a TLS channel (errorCode TLS CHANNEL) if the topmost layer of channel is not TLS. unstack is another name for unimport.

tlschan::handshake channel

Advances the handshake. Returns 1 once the handshake has completed and 0 if it is still in progress, which happens in nonblocking mode and inside the channel's -validatecommand; otherwise the command waits for the handshake to finish. If the handshake failed, raises its error message, such as handshake failed: certificate verify failed: certificate has expired, with errorCode TLS HANDSHAKE. A failed channel raises the same error on every later call.

tlschan::status ?-local? channel

Returns a dictionary describing the session and the peer's certificate, or with -local the local certificate. The dictionary is empty until the handshake has completed, and stays empty if it failed. The certificate keys are missing when there is no such certificate, for example on a server whose client sent none. Session keys:

protocol string

TLSv1.2 or TLSv1.3, as in tcltls.

cipher name

IANA name of the cipher suite, such as TLS_AES_256_GCM_SHA384.

sbits n

Key size of the symmetric cipher in bits: 128 or 256.

alpn protocol

The protocol agreed through ALPN, or an empty string.

servername name

On a client the -servername in use; on a server the name the client sent in the SNI extension. Empty if there is none.

The certificate keys are the same as in the cert argument of the -validatecommand callback:

certificate pem

The certificate in PEM format.

sha1_hash hex
sha256_hash hex

SHA-1 and SHA-256 digest of the DER certificate, in upper case hex.

subject dn
issuer dn

Distinguished names in RFC 2253 form, most significant part last, as in CN=localhost,O=Example,C=US. Special characters are escaped with a backslash; attributes of unknown type appear as oid=#hex.

serialNumber hex
serial hex

The serial number in upper case hex without leading zeros, preceded by - if negative. serial is the tcltls 1.7 name.

version n

Certificate version, normally 3.

signatureAlgorithm name
signature name

Signature algorithm of the certificate (outer and inner field), such as sha256WithRSAEncryption or ecdsa-with-SHA256; unknown algorithms appear as dotted OIDs.

notBefore time
notAfter time

Validity period as Oct 15 08:03:54 2026 GMT; the day of the month is padded to two characters with a space.

self_signed bool

Whether issuer and subject are the same name.

publicKeyAlgorithm name

Such as rsaEncryption, id-ecPublicKey or ED25519.

bits n

Size of the public key: the RSA modulus length, or the curve size for elliptic curve keys (256 for P-256). Missing if unknown.

extensions list

Names of the certificate's extensions in certificate order, dotted OIDs for unknown ones.

num_extensions n

Length of that list.

subjectAltName list

Subject alternative names, each as DNS:name, IP Address:address, email:address, URI:uri, DirName:/name or Registered ID:oid. IPv6 addresses are written as eight colon separated hex groups. Missing without the extension.

subjectKeyIdentifier hex
authorityKeyIdentifier hex

Key identifiers in upper case hex. Missing without the extension.

ocsp list

OCSP responder URLs from the authority information access extension. Missing if there are none.

ca bool

The CA flag of the basic constraints extension; 0 without it.

tlschan::connection channel

Returns a dictionary with the state of the connection, available at any time:

state state

handshake, open or failed.

is_server bool

Whether the channel is the server side.

servername name

As in status; before the handshake has completed, the -servername given. Absent when the state is failed.

error message

Only when the state is failed: the error message.

protocol cipher sbits alpn

Only when the state is open: as in status.

session_reused bool

Only when the state is open: whether the session was resumed, see SESSION RESUMPTION.

tlschan::init ?option value ...?

Sets the default options of tlschan::socket, both forms. Each call replaces the previous defaults; without arguments it removes them. -model, -server and -servername are dropped. The options are not checked until socket uses them. tlschan::import does not use these defaults. Returns an empty string.

tlschan::ciphers ?protocol? ?verbose? ?supported?

Returns the IANA names of the cipher suites the library offers for certificate based key exchange. protocol is one of ssl2, ssl3, tls1, tls1.1, tls1.2 or tls1.3; the list is empty for the first four. Without protocol, suites of both TLS 1.2 and TLS 1.3 are returned. verbose and supported are accepted for compatibility and ignored.

tlschan::protocols

Returns the protocols that can be enabled: tls1.2 tls1.3.

tlschan::version

Returns the name and version of the TLS library, such as wolfSSL 5.9.4, rustls 0.23.46, Mbed TLS 3.6.7 or OpenSSL 3.6.5.

tlschan::exporter channel label length ?context?

Returns length bytes of keying material exported from the session as defined by RFC 5705 (TLS 1.2) and RFC 8446 section 7.5 (TLS 1.3). length is 1 to 8160; context is a byte string. With TLS 1.2 leaving out context gives a different result from an empty one; with TLS 1.3 the two are the same. Errors: the TLS handshake has not completed (errorCode TLS WRONGSTATE), length must be between 1 and 8160 (TLS WRONGARGS) and keying material export failed (TLS EXPORT).

tlschan::randombytes count

Returns count bytes, 0 to 1048576, from the library's random number generator.

tlschan::aesgcm-encrypt key plaintext

Encrypts plaintext with AES-256-GCM, without associated data. key must be 32 bytes. Returns a fresh random 12 byte nonce, the ciphertext and the 16 byte tag, concatenated: 28 bytes more than plaintext.

tlschan::aesgcm-decrypt key data

Reverses aesgcm-encrypt: data is nonce, ciphertext and tag as returned by it. Raises ciphertext too short if data has fewer than 28 bytes and AES-GCM authentication failed if the tag does not match.

tlschan::pbkdf2 digest password salt iterations length

Derives length bytes, 1 to 64, from password and salt with PBKDF2 (RFC 8018). digest is sha1, sha256 or sha512, the HMAC hash. iterations is 1 to 10000000.

The arguments and results of randombytes, aesgcm-encrypt, aesgcm-decrypt and pbkdf2 are byte strings; a character above U+00FF raises a Tcl error, so convert text with encoding convertto utf-8 first. Their own errors have errorCode TLS CRYPTO.

tlschan::pkgconfig list
tlschan::pkgconfig get key

Build information as registered with Tcl_RegisterConfig. Keys: version, the package version (0.1.0), and backend, one of wolfssl, rustls, mbedtls or openssl.

tlschan::backend

Only in tlschan: returns the name of the backend it loaded, such as openssl.

OPTIONS

These options are accepted by import and starttls, by socket and by init. Boolean values are any form Tcl accepts. An empty value counts as not given for -cadir, -cafile, -cert, -certfile, -cipher, -ciphersuites, -command, -key, -keyfile, -model, -password, -servername, -validatecommand and -vcmd.

-alpn list

Protocol names to negotiate with ALPN (RFC 7301), such as h2 http/1.1. Each name must be 1 to 255 bytes long, or import raises invalid ALPN protocol name "" (errorCode TLS CONFIG). Which common name is chosen depends on the backend, see BACKEND DIFFERENCES. With none in common the handshake completes without ALPN.

-autoservername bool

Only meaningful to socket, see there. import ignores it.

-cadir directory

A directory of trusted CA certificates. The TLS library reads it directly, so it must be a native path, not one inside a Tcl virtual filesystem. The expected file names differ, see BACKEND DIFFERENCES. -cadir and -cafile can be combined.

-cafile file

Trusted CA certificates: a PEM file with any number of them, or one DER certificate. The file is read through Tcl's filesystem, so it can be inside zipfs or another virtual filesystem.

Without -cafile and -cadir the system trust store is used, read when first needed. Where it comes from depends on the backend, see BACKEND DIFFERENCES.

-cert data

The local certificate as data: PEM text, which may hold the leaf certificate followed by intermediates to be sent along, or a single DER certificate. Takes precedence over -certfile.

-certfile file

As -cert, read from a file through Tcl's filesystem.

-cipher list

The TLS 1.2 cipher suites to enable, replacing the default ones. The list holds suite names separated by colons, commas or white space: IANA names as ciphers returns them (TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256), the same with - for _, OpenSSL names (ECDHE-ECDSA-AES128-GCM-SHA256) or the library's own names, in any letter case. OpenSSL cipher string syntax (HIGH, !aNULL, @STRENGTH) is not supported. An unknown name raises unknown cipher: name (errorCode TLS CONFIG).

-ciphersuites list

The TLS 1.3 cipher suites to enable, replacing the default ones, in the same form, such as TLS_CHACHA20_POLY1305_SHA256.

Names of either protocol may appear in either option: each name is sorted to its protocol, and the names a protocol receives replace its defaults. A protocol that receives no names keeps its defaults, unless its own option was given: -cipher without a TLS 1.2 name disables TLS 1.2, and -ciphersuites without a TLS 1.3 name disables TLS 1.3. If that leaves no protocol, import raises no usable cipher suites (errorCode TLS CONFIG).

-command prefix

A command prefix invoked on handshake completion and on failure, see CALLBACKS.

-key data

The private key as data, PEM or DER: PKCS#8, PKCS#1 (RSA) or SEC1 (EC). Takes precedence over -keyfile. A certificate and a key must be given together, and they must match.

-keyfile file

As -key, read from a file through Tcl's filesystem. Defaults to the -certfile, so one PEM file can hold both.

An encrypted key needs -password. PKCS#8 keys encrypted with PBES2, as written by openssl pkcs8 -topk8 -v2 aes-256-cbc, work with every backend, in PEM and DER form. Other formats depend on the backend, see BACKEND DIFFERENCES.

-model channel

Use a shared configuration: certificates, keys, password, trust, protocols, cipher suites, ALPN, -request and -require come from it, and options of this call that configure them are ignored. -servername, -command and -validatecommand still apply. channel can be any channel. A TLS channel lends its own configuration. Any other channel anchors one: the first import naming it creates the configuration from its options, later imports share it, and it is released when channel is closed; channels using it keep it. -server must match the configuration, or import raises -model channel is configured as a client (or server), errorCode TLS MODEL. Sharing a configuration saves loading files again and is needed for session resumption, see SESSION RESUMPTION.

-password script

A script whose result is the password of the private key; the script may also end with return password. It is evaluated at global level, once, by the import that creates a configuration with a key, whether or not the key is encrypted. An error in the script is raised by import.

-request bool

On a server, ask the client for a certificate. Default 0. A certificate the client sends is then available through status whether or not it verifies, unless -require is set. No effect on a client.

-require bool

On a client, verify the server's certificate chain and host name and fail the handshake if they do not verify. Default 1. With 0, no verification is done, unless -validatecommand is given.

On a server, require a client certificate that verifies against -cafile, -cadir or the system store; implies -request. Default 0.

-server bool

Act as the server side. Default 0. A server needs a certificate and a private key, or import raises an error.

-servername name

On a client, the name sent in the SNI extension and the name the server's certificate must match. An IP address is matched against the certificate's IP address entries and is not sent as SNI. Without -servername no SNI is sent and only the chain is verified, not the name; unlike socket, import does not set it. A value that is neither a host name nor an IP address raises invalid server name "name" (errorCode TLS CONFIG). Servers ignore this option.

-ssl2 bool
-ssl3 bool
-tls1 bool
-tls1.1 bool
-castore uri
-dhparams file
-post_handshake bool
-security_level n
-session_id data

Accepted for tcltls compatibility and ignored; the old protocols are never enabled.

-tls1.2 bool
-tls1.3 bool

Enable TLS 1.2 or TLS 1.3. Both default to 1. Disabling both raises no protocols enabled (errorCode TLS PROTOCOL).

-validatecommand prefix
-vcmd prefix

A command prefix that decides on each certificate the peer sends, see CALLBACKS. A channel with this callback never resumes a session.

CALLBACKS

-command and -validatecommand are command prefixes: the arguments below are appended and the command is evaluated at global level. They can run inside any command that does I/O on the channel, or from the event loop when the channel is nonblocking. An error in a callback is reported through bgerror (see interp bgerror); it does not become the result of the command that triggered the callback.

prefix info channel handshake done {SSL negotiation finished successfully} info

-command, once, when the handshake has completed.

prefix error channel message

-command, once, when the channel fails, during the handshake or later. message is the error that I/O on the channel raises from then on.

prefix verify channel depth cert ok error

-validatecommand, during the handshake, for each certificate the peer sent, from the highest depth down to 0, the peer's own certificate. Certificates taken from the local trust store are not reported. cert is a dictionary with the certificate keys of status. ok is 1 if the library accepts this certificate and 0 if not; error then gives the reason, such as certificate has expired, hostname mismatch or issuer certificate not trusted for a certificate signed by a rejected one, and is empty otherwise.

A result that is a true boolean or a nonzero integer accepts the certificate. Anything else, or an error, rejects it, and the handshake fails with handshake failed: certificate rejected by validation callback. The result replaces the library's verdict whatever -require says: the callback can accept an expired or untrusted certificate or a name mismatch, and can reject a valid one. A client calls it whenever it is given; a server only with -request or -require, when the client sends a certificate.

The callback may use its channel, but the handshake is still in progress: handshake returns 0, reads return nothing, and what it writes is sent once the handshake has completed.

The -password script is not a prefix: it is evaluated as given, without arguments, see OPTIONS.

CHANNEL BEHAVIOUR

  • The TLS channel keeps the name of the channel below. It adds no channel options of its own: chan configure options other than the generic ones, such as -peername, -sockname or -keepalive, are those of the channel below.

  • The handshake starts on first use. On a blocking channel the first read, gets, flush or tlschan::handshake performs the whole handshake and waits for it. On a nonblocking channel the handshake proceeds from the event loop: at once if the channel was already nonblocking when imported, otherwise after the first read or write attempt or once a chan event handler is set. tlschan::handshake also advances it. Data written before it completes is buffered and sent afterwards. Readable and writable handlers are not called before the handshake has completed or failed.

  • A failure is final: every later read, gets, puts or flush raises the error, without errorCode, and a nonblocking channel becomes readable and writable to report it. During the handshake the message is handshake failed: reason; afterwards read failed: reason, write failed: reason, connection closed or an operating system message such as connection reset by peer. Either way it can also be peer sent alert: description. Typical handshake reasons are certificate verify failed: why, certificate rejected by validation callback, peer did not return a certificate and connection closed during handshake; why is one of certificate has expired, certificate is not yet valid, hostname mismatch, self-signed certificate, unable to get local issuer certificate or issuer certificate not trusted, or else the library's own words.

  • In TLS 1.3 a client's handshake completes before the server has checked the client certificate. A rejection reaches the client as an alert on its next read, as in peer sent alert: certificate required.

  • The end of the stream is reported as EOF both when the peer sent a close_notify alert and when the connection was closed without one.

  • close sends a close_notify alert if the handshake has completed, writes out pending data, blocking if needed, and closes the channel below. Tcl refuses to half-close a stacked channel: close channel write raises half-close not applicable to stack of transformations.

  • fcopy and chan copy work in both directions.

SESSION RESUMPTION

All backends resume sessions, in TLS 1.2 and TLS 1.3, by the same rules:

  • A server issues session tickets under a key that belongs to its configuration, so it resumes only sessions of connections that shared that configuration. The connections accepted by one socket -server share one.

  • A client keeps the most recent session for each server name, for up to 32 names, in its configuration, and offers it on the next connection to the same -servername that uses this configuration. A client therefore resumes only when its connections share a configuration through -model, for example one anchored on a long-lived channel:

    set model [file tempfile]
proc https {args} {
    tlschan::socket -model $::model {*}$args
}
http::register https 443 https

  • There is no resumption for a client without -servername, nor for a client or a server with -validatecommand, whose callback must see every handshake.

  • connection reports whether a session was resumed as session_reused.

BACKEND DIFFERENCES

The backends behave alike except for the following, observed with wolfSSL 5.9.4, rustls 0.23.46, Mbed TLS 3.6.7 and OpenSSL 3.6.5.

Cipher suites

tlschan::wolfssl and tlschan::rustls have 3 TLS 1.3 suites and 6 TLS 1.2 suites, all ECDHE with AES-GCM or ChaCha20-Poly1305. tlschan::mbedtls and tlschan::openssl add the CCM suites to TLS 1.3 and offer many more TLS 1.2 suites (103 and 59 in the builds above), including CBC, ARIA, Camellia, DHE and RSA key exchange; their lists depend on how the library was built.

ALPN choice

tlschan::wolfssl chooses the first of the client's protocols that the server also lists; the others choose the first of the server's protocols that the client offers.

-cadir

tlschan::wolfssl and tlschan::mbedtls load every certificate file in the directory. tlschan::rustls loads files named "*.pem", "*.crt" or like an OpenSSL hash link ("1a2b3c4d.0"). tlschan::openssl needs an OpenSSL hashed directory (see openssl rehash) and finds only certificates under their hash names.

Trust anchors

tlschan::openssl also accepts a certificate that is not a CA, given in -cafile, as a trust anchor; the others do not.

System trust store

tlschan::wolfssl uses the Windows or macOS store, elsewhere the certificates in "/etc/ssl/certs", "/etc/pki/ca-trust/source/anchors" and "/etc/pki/tls/certs", or if none exists the bundle "/etc/ssl/cert.pem" (on Haiku "/boot/system/data/ssl/CARootCertificates.pem"); it ignores SSL_CERT_FILE and SSL_CERT_DIR. tlschan::rustls uses rustls-native-certs, which honours SSL_CERT_FILE and SSL_CERT_DIR, and falls back to Mozilla's root list when the system has none. tlschan::mbedtls reads SSL_CERT_FILE and SSL_CERT_DIR if set, else the first CA bundle found at the usual places, else "/etc/ssl/certs"; on Windows it uses the Windows certificate store, on macOS the keychain's trust settings. tlschan::openssl uses OpenSSL's default locations, which honour SSL_CERT_FILE and SSL_CERT_DIR, then the usual bundle files, and on Windows with OpenSSL 3.2 or later the Windows store.

Encrypted keys

Legacy encrypted PEM keys (Proc-Type: 4,ENCRYPTED) and PKCS#8 keys encrypted with PBES1, such as PBE-SHA1-3DES, work only with tlschan::mbedtls and tlschan::openssl; tlschan::wolfssl reports unsupported key encryption for them.

Refused client certificates

The alert a server sends when it refuses a client certificate is the library's. For a missing certificate it is certificate required in TLS 1.3; in TLS 1.2 tlschan::wolfssl and tlschan::openssl send handshake failure, tlschan::rustls certificate required, and tlschan::mbedtls closes the connection without an alert, so the client reports connection closed during handshake. For an untrusted certificate it is unknown CA, from tlschan::rustls certificate unknown. A tlschan::mbedtls server in TLS 1.3 encrypts the alert with keys the client no longer reads with, so the client's next read fails with a MAC error instead (an Mbed TLS bug); the server still refuses.

Received alerts

tlschan::mbedtls reports a received alert as peer sent alert without its name: Mbed TLS 3.6 doesn't say which one arrived.

COMPATIBILITY

tcltls

Code written for tcltls 2 mostly runs unchanged through the ::tls aliases of tlschan, or with ::tls replaced by ::tlschan or a backend's namespace. The differences:

  • Not provided: tls::shutdown, tls::misc, tls::build-info, the sample callbacks tls::callback, tls::password and tls::validate_command, and tls::debug. Added: exporter, randombytes, aesgcm-encrypt, aesgcm-decrypt and pbkdf2.

  • status: cipher is an IANA name, also for TLS 1.2, where tcltls uses OpenSSL names; digests are upper case hex; bits is the key size, not its security strength. tcltls keys not listed under status, such as peername, verifyResult, keyUsage or all, are absent; self_signed, ca, num_extensions and ocsp correspond to tcltls's selfSigned, basicConstraintsCA, extCount and ocspResponders.

  • connection: state is handshake, open or failed, not an OpenSSL state string, and only the keys listed there exist.

  • ciphers returns IANA names and ignores verbose and supported.

  • -command reports only info (handshake completion) and error; there are no message and session calls.

  • -validatecommand is called only with verify, not with alpn, hello or sni. Any true result accepts; tcltls treats 2 as rejecting without aborting. Certificates from the local trust store are not reported.

  • -password is evaluated without arguments; tcltls appends password, the read/write flag and the maximum length.

  • -cert and -key take PEM as well as DER; -cafile, -certfile and -keyfile are read through Tcl's filesystem.

  • Options without an effect here are accepted and ignored, see OPTIONS.

  • errorCodes begin with TLS, see ERRORS.

tclmtls

tclmtls is the package mtls with commands in ::mtls; its names do not clash with these packages. Compared with tclmtls:

  • There is nothing like mtls::debug or mtls::build-info.

  • tlschan::pkgconfig has only the keys version and backend; tclmtls's client, server, proto,protocol and version,backend, name,backend, type,backend are absent.

  • status returns more keys, and cipher suites, there and in ciphers, are IANA names (TLS_AES_256_GCM_SHA384) instead of Mbed TLS names (TLS1-3-AES-256-GCM-SHA384).

  • errorCodes begin with TLS instead of MTLS, and errors of the crypto commands are just TLS CRYPTO, without a further element. The crypto commands take and return data in the same formats and with the same limits.

ERRORS

Errors raised by the commands have these errorCodes:

TLS CONFIG

An invalid option value: unparsable certificate, key or CA file, wrong password, unknown cipher suite, invalid ALPN name or server name, missing certificate on a server.

TLS PROTOCOL

No protocol enabled.

TLS MODEL

The -model configuration is for the other side, client or server.

TLS IMPORT

The session could not be set up.

TLS CHANNEL

The channel is not a TLS channel.

TLS HANDSHAKE

Raised by handshake for a failed handshake.

TLS WRONGSTATE TLS WRONGARGS TLS EXPORT

Raised by exporter.

TLS CRYPTO

Raised by the crypto commands.

TLS INIT

The library could not be initialised when loading the package.

TLS BACKEND

tlschan found no backend to load.

Errors opening a file named in an option have a POSIX errorCode; errors in arguments have the usual TCL ones. I/O errors on the channel do not set errorCode, see CHANNEL BEHAVIOUR.

STATIC LINKING

Built with BUILD_SHARED_LIBS=OFF, each backend is an archive, such as "libtcl9tlschan_wolfssl0.1.0.a", whose only global symbol is its initialisation function: Tlschan_wolfssl_Init, Tlschan_rustls_Init, Tlschan_mbedtls_Init or Tlschan_openssl_Init. The archive uses Tcl's stubs interface, so the application also links Tcl's stub library; the pkg-config file "tcl9tlschan_wolfssl.pc" (and so on) names the other libraries to link. The application registers the package and declares it in each interpreter that is to use it:

Tcl_StaticLibrary(NULL, "Tlschan_wolfssl", Tlschan_wolfssl_Init, NULL);
Tcl_EvalEx(interp,
    "package ifneeded tlschan::wolfssl 0.1.0 {load {} Tlschan_wolfssl}", -1, 0);

Pass NULL, not an interpreter: with one, Tcl takes the package as already loaded there and never calls Tlschan_wolfssl_Init. There is no safe-interpreter initialisation function.

tlschan is a script, installed with its "pkgIndex.tcl" in "lib/tlschan0.1.0" for static builds too. An application ships it in its script library, next to the backends it registers, and package require tlschan then picks among those. See "README.md" for building.

EXAMPLES

Fetch a page over HTTPS, verifying the server against the system store:

package require tlschan
package require http
http::register https 443 ::tlschan::socket
set tok [http::geturl https://www.tcl-lang.org/]
puts [http::ncode $tok]
http::cleanup $tok

An echo server, event driven:

package require tlschan
proc accept {chan addr port} {
    chan configure $chan -blocking 0 -buffering line
    chan event $chan readable [list echo $chan]
}
proc echo {chan} {
    if {[catch {gets $chan line} n]} {
        puts stderr "$chan: $n"
        close $chan
    } elseif {$n >= 0} {
        puts $chan $line
    } elseif {[eof $chan]} {
        close $chan
    }
}
set opts {-certfile server.pem -keyfile server-key.pem}
tlschan::socket -server accept {*}$opts 8443
vwait forever

Switch an established plain connection to TLS, as after a STARTTLS command; -servername must be given explicitly:

package require tlschan
set chan [socket mail.example.com 587]
# ... plain text exchange ending in STARTTLS ...
tlschan::starttls $chan -servername mail.example.com
tlschan::handshake $chan

Accept a server only if its certificate has a known SHA-256 fingerprint, such as one shown by openssl x509 -noout -fingerprint -sha256. This one pins the backend by requiring it directly:

package require tlschan::mbedtls
proc pin {fingerprint op chan depth cert ok error} {
    if {$depth > 0} {
        return 1
    }
    set expected [string map {: ""} $fingerprint]
    string equal -nocase $expected [dict get $cert sha256_hash]
}
set vcmd [list pin $fingerprint]
set chan [tlschan::mbedtls::socket -validatecommand $vcmd device.local 8443]

Mutual TLS: the server requires a client certificate issued by its CA and greets the client by name.

package require tlschan
proc accept {chan addr port} {
    chan configure $chan -blocking 0 -buffering line
    chan event $chan readable [list greet $chan]
}
proc greet {chan} {
    if {[catch {gets $chan line} n] || [eof $chan]} {
        close $chan
    } elseif {$n >= 0} {
        puts $chan "hello [dict get [tlschan::status $chan] subject]"
    }
}
set opts {-certfile server.pem -keyfile server-key.pem}
tlschan::socket -server accept -require 1 -cafile client-ca.pem {*}$opts 8443
vwait forever

The client:

package require tlschan
set opts {-certfile client.pem -keyfile client-key.pem}
set chan [tlschan::socket -cafile server-ca.pem {*}$opts server.example.com 8443]
chan configure $chan -buffering line
puts $chan hi
puts [gets $chan]

Code written for tcltls, unchanged:

package require tlschan
set chan [tls::socket www.tcl-lang.org 443]
